# AI 기능 효과 측정 (2026-11-17)

AI가 맡은 두 가지 일을 실제 실행 결과로 측정했습니다.

1. **테스트 생성:** 요구사항과 요청 문장으로 브라우저 테스트 단계를 만든다.
2. **실패 분석:** FAIL의 원인이 테스트 쪽인지 제품 쪽인지 구분한다.

모델은 `gpt-4.1-mini`, 브라우저는 Microsoft Edge(Playwright channel)를 사용했습니다. 원자료는 [`experiments/results/`](../experiments/results/)에 있고, 같은 명령으로 다시 측정할 수 있습니다.

## 1. 페이지 구조 전달이 테스트 생성에 미치는 효과

**방법**
- 대상 페이지 두 곳에서 시나리오를 5개씩 준비했습니다.
  - 로그인 데모: `data-testid`가 있습니다.
  - 실험용 회원가입 페이지: `data-testid`가 없고 id·name이 흔한 관례와 다릅니다. 가입하면 `/welcome`으로 이동합니다.
- 같은 요구사항과 요청 문장을 세 조건으로 3번씩 AI에 보냈습니다. 조건마다 30회, 모두 90회이고, 요청 문장에는 선택자를 넣지 않았습니다.
  - **구조 없음:** 요구사항과 요청 문장만 전달
  - **시작 페이지 구조:** 등록 URL에서 읽은 요소·선택자를 함께 전달
  - **시작+이동 후 페이지 구조:** 위에 더해 링크·요구사항에 적힌 같은 사이트 경로(예: `/welcome`)를 조회만 해서 읽은 구조까지 전달
- 생성된 테스트는 **사람이 고치지 않고** 형식 검사 → 선택자 확인 → QA 실행기로 실제 실행했습니다.

| 지표 | 구조 없음 | 시작 페이지 구조 | 시작+이동 후 페이지 구조 |
|---|---|---|---|
| **수정 없이 실행해 PASS** | 13/30 (43.3%) | 28/30 (93.3%) | **30/30 (100%)** |
| FAIL (테스트가 틀림) | 5 | 2 | 0 |
| ERROR (요소를 못 찾거나 여러 개와 겹쳐 실행 불가) | 12 | 0 | 0 |
| 읽은 페이지에서 정확히 1개 요소와 일치한 선택자 | 89/149 (59.7%) | 169/171 (98.8%) | 167/169 (98.8%) |
| 모든 선택자가 정확한 테스트 | 2/30 (6.7%) | 28/30 (93.3%) | 28/30 (93.3%) |
| 평균 생성 시간 | 4.53초 | 4.27초 | 4.19초 |

시작 페이지를 읽는 데는 회원가입 4.4초, 로그인 데모 9.2초가 걸렸습니다(생성 시간과 별도). AI 호출은 90회 모두 성공했습니다.

| 대상 | 구조 없음 PASS | 시작 페이지 구조 PASS | 시작+이동 후 PASS |
|---|---|---|---|
| 로그인 데모 (`data-testid` 있음) | 13/15 | 15/15 | 15/15 |
| 회원가입 (`data-testid` 없음) | **0/15** | 13/15 | **15/15** |
| └ "정상 가입" (가입 후 `/welcome` 확인) | 0/3 | 1/3 | **3/3** |

- **선택자를 짐작하기 어려운 페이지일수록 효과가 컸습니다.** 구조를 주지 않으면 AI는 `#email`, `input[type='password']` 같은 흔한 선택자를 짐작했습니다. 이 선택자들은 페이지에 없거나, 비밀번호 입력창 2개처럼 여러 요소와 겹쳐 실행되지 않았습니다.
- **이동 후 페이지 구조는 "이동한 뒤의 확인" 실패를 없앴습니다.** 시작 페이지만 주면 AI는 환영 페이지의 제목도 시작 페이지처럼 `h2`일 것이라고 짐작했습니다(실제는 `h1`). `/welcome`을 함께 읽어 주자 3번 모두 맞는 선택자를 썼습니다.
- 로그인 후 홈(`/home`)처럼 로그인이 필요한 페이지는 조회만으로는 읽을 수 없어 "접근 제한"으로 전달됩니다. 이 시나리오는 요구사항 문장("로그인 완료" 제목)만으로도 통과했습니다.

이전 측정(2026-11-16, 구조 없음 / 시작 페이지 구조 두 조건)에서는 PASS가 40% → 90%였고, 남은 실패 3건이 모두 위의 `h2` 짐작이었습니다. 이번 측정은 그 원인을 해결한 기능을 같은 조건에서 다시 잰 것입니다.

## 2. AI 실패 분석의 원인 구분 정확도

| 실패 종류 (정답) | 표본 | 결과 |
|---|---|---|
| 이번 실험에서 AI가 만든 테스트가 틀린 경우 (**테스트 정의 문제**) | 7건 | **7/7** |
| 이전 실험의 같은 종류 실패 | 9건 | 9/9 (지시문 보강 전 7/9) |
| 의도적으로 넣은 제품 결함 6종 × 3회 (**제품 결함**) | 18건 | **18/18** |

- 처음 지시문은 `h1`/`h2` 사례 2건을 "제품 결함"으로 분류했습니다. 분석 설명은 "선택자 불일치"라고 정확히 짚었지만 분류만 달랐습니다.
- 그래서 지시문을 보강했습니다. 요구사항에 없는 태그 종류는 제품의 약속이 아니라는 점, 분류와 제안이 서로 모순되지 않아야 한다는 점을 추가했습니다.
- 같은 9건을 보고 고쳤기 때문에 과적합을 두 가지로 점검했습니다.
  - 실제 제품 결함 18건은 **결함 표시·테스트 이름·결함 설명을 가리고** 요구사항과 실행 증거만 전달했는데도 모두 제품 결함으로 분류했습니다.
  - 지시문을 고친 뒤 새로 나온 실패 7건도 모두 맞혔습니다.

## 한계

- 표본이 작습니다(페이지 2개, 시나리오 10개, 모델 1개). 회원가입 페이지는 이 실험을 위해 만든 페이지입니다.
- 선택자 확인은 선택자가 읽은 페이지 **중 어딘가에서** 정확히 1개와 일치하는지만 봅니다. 그 단계가 실행되는 페이지와 같은지는 실행 결과(PASS/FAIL)로 판단합니다.
- 로그인이 필요한 페이지는 조회만으로 읽을 수 없습니다. 이런 페이지의 요소는 여전히 요구사항 문장과 AI의 추정에 의존합니다.
- 기획서의 "유효 TC 비율"은 테스트가 요구사항에 맞는 의미 있는 검사인지 사람이 판단해야 하는 지표입니다. [CSV](../experiments/results/ai-quality-20261117-2130.csv)의 `수동 판정` 열에 기록해 마무리해야 합니다.
- 수동으로 테스트를 작성할 때 걸리는 시간과의 비교는 아직 측정하지 않았습니다.
